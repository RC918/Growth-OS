# AI Company Growth OS｜執行藍圖 v1.0

日期：2026-09-27　狀態：v1.5；首個系統設計完成；電商／貿易商市場、新品牌、新網域、零資料起步；90 天現金預算上限已核准；未接入真實帳號、未上線

## 1. 要驗證的生意

目標客戶改為電商與貿易商；第一個狹窄切入點是**有自營網站、管理多個商品或規格，並向海外或多語市場銷售的中小型商家**。這個交集同時需要商品資料、搜尋能見度和詢問／訂單追蹤。Owner 本身有小企業實務經驗，先以其真實作業建立第一份問題圖譜與測試情境，清楚標記為「創辦人經驗」；之後才用外部商家驗證可遷移性。內部試點是 Good Morning Digital Co., Ltd. 旗下**全新產品與全新網域**；Morning Ai 不作試點網站。工作標題採 `Growth OS by Good Morning Digital`；這是產品描述而非已清理權利的獨占品牌。正式產品名稱、網域及商標須另行確認；工程代號仍為 `Growth OS Pilot`。

核心承諾：每週找出一項有依據的獲客或轉換機會，協助執行，回報可追溯的廣告來源、訪問、合格詢問及成交。首個創辦人問題是 Facebook、Telegram、LINE／簡訊廣告導流至官網後，訪客未註冊便離開。先確認「註冊」是否必要，以及點擊、抵達、互動、詢盤／結帳各步的真實流失；沒有舊數據時不推定原因。無法追蹤到成交時明確標示「未歸因」。

最短工作循環：`連接網站 → 建立基線 → 提議機會 → 人審資料和動作 → 執行一項 → 標記發布時間 → 比較前後和對照 → 報告證據與不確定性 → 下一項`。

## 2. 產品邊界與階段

| 階段 | 交付與驗收門檻 | 暫不納入 |
|---|---|---|
| 0，問題驗證，約 2–3 週 | 創辦人真實電商／貿易作業情境和公開需求資料；問題清單、方案假設、預算門檻、首個診斷工具規格；名稱候選與新站量測方案 | 大量頁面、付費 Ahrefs、全自動代理 |
| 1，單站閉環，約 4–8 週 | 一個網站，10–20 個候選機會，選 3–5 個具獨特資料的頁面或更新；至少一項實際發布、一份有來源的週報、一項可驗證的轉換事件 | 多租戶、供應商管理、財務 ERP、全球自動擴張 |
| 2，外部驗證，約 8–12 週 | 3–5 個有授權的電商／貿易商真實站；驗證創辦人情境是否具共通性；完成連接、首個成果、每週回訪；記錄無成效、拒絕與流失原因 | 按文章數收費 |
| 3，付費 MVP，需通過階段 2 | 自助註冊和權限、訂閱、個別網站隔離、可撤銷授權、可下載原始證據；取得實際付費和續訂數據 | 市集、全自動投放、跨國稅務引擎 |
| 4，擴張 | 多語、多市場、實驗與分發、更多來源、Agency 工作區；按使用需求排序 | 預先承諾 12 個月必完成 |

每一階段以證據放行，不以日曆自動放行。階段 1 若沒有可歸因的 lead，仍可完成儀表板，但不能宣稱「證明 Growth」。

## 3. 第一版實際功能

1. **Business Profile**：產品、客群、地區、禁止宣稱、轉換目標、品牌實體與既有網頁；Owner 核准。
2. **Opportunity Queue**：GSC query/page、站內搜尋與客戶問題匯入；記錄來源、需求代理訊號、差異價值、資料可得性、商業相關性、成本與信心。人工審核前不發布。
3. **Evidence Registry**：每項價格、規格、產品宣稱綁定來源 URL、抓取時間、有效日期、校驗者。數據直接渲染；LLM 只能撰寫待核文案，不能編造數字。
4. **Action Log**：提議、核准、已執行、已發布、撤回；記錄 URL、版本、責任人、成本、時間、對照組和回滾方式。
5. **Visibility & Proof**：GSC 一般搜尋和生成式搜尋報表分開標示；GA4 的訪問/轉換和 CRM 成交按各自定義展示；Ahrefs 作選配競品情報。每個數字附來源、觀測窗與延遲。
6. **Weekly Growth Agent**：產出含「觀測、合理推論、未知、建議動作」四欄的週報；高影響動作先請 Owner 核准。

介面維持 Home、Opportunities、Growth、Visibility、Business 五項。沒有資料時顯示「尚未連接／尚未量測」，不能顯示示範數值當作真實成果。

## 4. 第一個試驗設計

新品牌初期問題領域定為「商家從廣告或搜尋取得訪客之後，為何沒有產生詢盤或訂單」。先把 Owner 的真實廣告經驗作問題來源，建立 Visitor-to-Customer Leak Map：公開掃描只指出可觀察的著陸頁摩擦；經商家授權後，才依 GA4、廣告與訂單/CRM 資料量測真正漏斗。目標成果是有效詢盤或淨訂單，註冊只是中間事件。SEO/GEO 與商品資料仍在後續獲客擴張模組，並在首版診斷中做基礎可見性檢查。待有原型後再訪談少量外部商家，避免把創辦人的特殊情境誤當普遍需求。產品尚未實作的功能標示「開發中」，不能作性能、客戶成果或收入宣稱。詳見《Commerce_Growth_首個診斷工具規格.md》。

第 0 天設定 GSC、GA4、表單/候補名單事件和站點所有權。新站沒有歷史基線；從上線日期起累積週趨勢，也以工具完成率、合格候補名單和實際試用作更早的需求指標，不能主張因果。商家的主要轉換分兩條：電商為訂單／毛利／退款；貿易商為合格詢盤／報價／成交。先做 3–5 個有原創價值的頁面，人工核准再發布；每週檢查抓取/索引、query、頁面與 CTA。至少觀察 8–12 週後才判斷 SEO 初期方向，不承諾一定見到排名。

**成功條件**：至少 1 頁有實際索引和相關 query 的曝光；免費工具被真實目標客戶完成、或產生合格試用詢問；展示一條可核對的行動至結果證據鏈；設計夥伴願意再次使用或付費。第一批數值門檻要在訪談後按實際基數設定。這是逐層驗證，不是承諾排名與營收。

**停止／轉向條件**：資料授權無法取得、每頁無獨特價值、維護單位成本超過預期效益、轉換定義不可靠、連續實驗沒有實際需求證據。記錄原因後縮小範圍或換市場。

## 5. 資料模型與連接器

核心表：`organizations`, `sites`, `business_profiles`, `source_connections`, `entities`, `claims`, `claim_sources`, `opportunities`, `actions`, `approvals`, `content_versions`, `page_daily_metrics`, `conversion_events`, `revenue_events`, `proof_links`, `audit_events`。每筆資料有 `organization_id`；跨租戶隔離、最小 OAuth 範圍與秘密輪替在進入付費多租戶前驗收。

`proof_links` 連接 action → page → observation → event；包含 `evidence_type`（observed/associated/estimated）、`source`, `collected_at`, `window_start/end`, `method`, `limitations`。同一交易 ID 去重，退款和取消沖回。僅當 CRM/訂單能確定連到 lead 與 action，才顯示「歸因營收」；其他情況顯示「相關期間營收」或未知。SEO 觀測數據不能單獨建立因果。

連接順序：GSC 手動匯出或 OAuth → GA4 → 自有表單/CRM → Ahrefs 只在有授權和商業需求時啟用。Ahrefs API 使用量與多客戶展示權利須實際查訂閱與合約；設限額、快取、來源註記，避免透支。先不強制依賴其 API。

2026-09 官方資訊：Google 已推出 Search Console 生成式 AI 獨立報表，但目前公開的 Search Analytics API 文件 `type` 僅列 web/image/video/news/discover/googleNews。**不能預設生成式報表已可由 API 擷取**；第一階段以介面匯出或有核准的替代取得方式驗證，再實作對應連接器。Ahrefs Brand Radar 有 mentions/citations 等 API，但屬其樣本與模型，不能與 GSC 曝光或真實訪問相加。

## 6. 任務與批准規則

| 動作 | 系統行為 |
|---|---|
| 收集資料、生成草稿、內部比對、建立週報 | 可自動執行，保留記錄 |
| 修改正式頁面、公開比較或價格宣稱、發送對外內容 | 先預覽、事實查核與 Owner/受委託編輯批准；可回滾 |
| 付費廣告、訂閱採購、外部發布合作、變更付款或資料共享 | 明示金額與影響後由 Owner 核准 |
| 刪除或 410、網站遷移、大量頁面發布 | 個別審查依據、影響範圍與復原計畫 |

營運代理依資料/動作區分，不需第一版同時建九個獨立 AI Agent。採事件與狀態機；複雜流程真有需要時再導入 LangGraph。第一版以 PostgreSQL 常規欄位加 JSONB 變動屬性，不預設所有東西用 EAV/pgvector。

## 7. 原計畫校正

- 結構化來源和人審能降低幻覺，不保證 100% 正確；價格會變、來源可能失效。
- Google Indexing API 僅適用特定職缺/直播頁；一般 pSEO 用 sitemap、正常內鏈、可抓取與內容品質。
- Schema 是讓符合規範的內容有機會呈現特定搜尋外觀，不保證 Rank 0；Core Web Vitals 應看實際指標，不能把 Lighthouse 95 分當流量保證。
- 90 天低曝光先診斷意圖、季節、索引、內容與競爭，再決定補強、合併或移除。
- AI 提及、被引用、搜尋曝光、訪問、lead、收入是不同口徑；統計來源、分母、樣本與時間須可見。
- 早期關鍵里程碑是單一有效需求與使用者留存，不是假設 500–2,000 頁後自然變現。

## 8. 工程交付順序與驗收

1. **資料字典和事件定義**：一份轉換/收入/合格 lead 定義、同意與授權流程；空值處理。
2. **資料管線**：GSC/GA4 匯入、重複匯入冪等、來源時間、權限失效提示；原始資料保存與可刪除。
3. **單站 UI**：機會清單、行動核准、可追溯證據鏈、五選單首頁與未知狀態。
4. **內容試驗**：資料來源查核、3–5 篇實際有用的內容、預覽/發布/回滾。
5. **週報**：把直接觀測與推論分開，清楚指出下一個決策。
6. **設計夥伴和收費實驗**：採訪、使用記錄、願付價格與實際付費，之後才擴多租戶。

每個階段交付：程式與 migration、資料契約、權限矩陣、樣本來源、驗收記錄、Staging 網址與測試結果。正式網站測試只在得到 Owner 的帳戶存取/上線批准後進行。
