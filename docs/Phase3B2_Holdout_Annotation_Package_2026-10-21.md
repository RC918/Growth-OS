# Phase 3B.2 獨立保留測試集標註工作包

狀態：`AWAITING_INDEPENDENT_ANNOTATION`（等待獨立標註）
資料：`prototype/ai-seo/fixtures/claim-holdout-v1.json`（30 筆，編號 h01–h30）

## 這份工作包要做什麼

Growth-OS 有一個「Claim-Based 驗證原型」，用來判斷 AI 生成的商品文案是否有來源證據。
在它能影響任何正式判定之前，必須先有一組它從未看過、也不是由開發者定案的測試題，
由不參與開發的人獨立判讀。本文件就是給標註者的工作說明。

重要誠實聲明：目前 30 筆題目的 `expected_decision` 是工程團隊的「預標註」，
只是待驗證的假設，不是標準答案。完成本工作包前，人工標註筆數為 0，
不得對外宣稱這組資料是「真人標註」或用它計算真實準確率。

## 獨立性規則（標註期間必須遵守）

1. 標註者不得看原型的輸出、規則或分數；判讀期間不得與開發者討論個別題目。
2. 標註者只根據每題附的來源證據（`evidence` 的引文）判讀，不使用對商品的外部知識。
3. 本保留集在標註完成前不得用於調整原型規則、提示詞或門檻；發現題目本身有誤，
   只記錄問題，不 悄悄改題。
4. 標註結果以新檔案回傳（見下），不得直接改寫工程預標註；兩者差異要保留供裁決。

## 每題的判讀方式

逐題閱讀 `text`，對照 `evidence` 中的 Fact ID、Citation ID 與引文，給出一個判定：

| 判定 | 意義 |
|---|---|
| PASS | 每個事實主張都能在證據中找到出處 |
| PASS_WITH_REVIEW | 沒有無證據或矛盾主張，但需要人讀過才能確認（如中文改寫、保留未解決衝突） |
| FAIL_CLOSED | 至少一個主張無出處、與證據矛盾、把未解決衝突當成定論，或引用 UNKNOWN 事實 |
| REVIEW_ADJUDICATION | 題目本身涉及規格未定的判讀原則（如「正確的否定句」該如何判），需要裁決者先定規則 |

同時記錄：判定理由（一句話）、不同意工程預標註與否、信心（高／中／低）。

## 爭議裁決規格

1. 每題由兩位標註者獨立判讀；結果一致即定案。
2. 不一致時，由第三位裁決者在看不到雙方身分與原型輸出的情況下，
   依證據與本文件定義裁決，並寫明裁決理由。
3. 若分歧來自判定定義不足（例如否定範圍），裁決者必須先把新規則寫進本节附錄，
   再回頭重判所有同類題目，不得逐題臨時決定。
4. `REVIEW_ADJUDICATION` 題目不計入原型對錯統計，直到裁決規則定案並完成重判。
5. 標註者與裁決者的身分、日期、每題判定與理由，連同與預標註的差異表，一併保存。

## 完成條件與尚缺事項

開始人工標註前尚缺（需 Owner 或專案負責人安排）：

- 兩位不參與本原型開發的標註者與一位裁決者（可為產品／內容背景，不需工程背景）。
- 標註結果回傳格式的確認（建議每題一列：id、判定、理由、信心、標註者代號）。
- 裁決附錄的存放位置確認（本文件附錄或獨立裁決紀錄）。

完成條件：30 題全數完成雙人標註、分歧全數裁決、`REVIEW_ADJUDICATION` 題目完成規則
定案與重判，並產出「預標註 vs 定案」差異表。在此之前，本保留集維持未啟用狀態，
原型不得接正式發布路徑，也不得以本集結果宣稱準確率。
