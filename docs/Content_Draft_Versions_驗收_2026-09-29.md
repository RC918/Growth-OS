# 執行準備排序與內容草稿版本｜獨立 Staging

## 規則與範圍

- 工作台依資料缺口、已核准可備稿、待審核、不採納排列。相同層級按建立時間與 ID 穩定排序。這是工作流程順序；沒有量測的搜尋量、流量、商業成果及工作量不參與排序。
- `content_versions` 僅存草稿，每筆保存所屬租戶、機會、遞增版本號、標題、正文、建立者及建立時間。沒有發布或覆寫動作，沒有接觸真實客戶資料。
- owner 專用 RPC 必須檢查租戶角色、機會核准狀態、來源與核准決策。資料表對登入成員只開放 RLS 限定的 SELECT，沒有直接 INSERT、UPDATE 或 DELETE 權限。

## 已完成的驗證

- Supabase 獨立 Growth OS Staging migration `content_draft_versions`（版本 `20260929143139`）已套用。SQL 回滾測試：owner 建立第 1／2 版及稽核紀錄；空內容、未核准機會、viewer 寫入、跨租戶讀寫均遭拒絕。測試交易已回滾，不保留草稿資料。
- 本地網頁測試 10 項通過，包含排序、owner/viewer API 呼叫及預覽檔案與原型一致。
- Supabase security advisor 未回報此次新表或函式的問題；原有的 `auth_leaked_password_protection` 警告仍存在。
- 2026-09-29 晚上以真實 owner 測試登入送出一筆合成草稿；畫面出現「已完成，資料已更新」，資料庫查得該機會的第 1 版草稿、標題與正文。這驗證了真實 owner 的寫入路徑。送出後視窗停在工作台頂端，導致使用者看不到卡片內新增的版本，已修正為送出後展開版本紀錄並移到該卡片，同時改善草稿欄位排版。

新介面的展開與捲動畫面、viewer 真實帳號的版本讀取仍待網頁端到端驗收。本階段不發布內容，也不宣稱獲得真實流量或收益。
